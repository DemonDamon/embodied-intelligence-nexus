# AIRSEAI 1.0：Linux Foundation 托管的开源具身机器人软件栈

> 作者：Damon Li | 更新日期：2026年8月27日
> 证据状态：**官方披露与官方开源代码**。Linux Foundation 于 2026 年 8 月 26 日宣布 AIRSEAI 加入 LF AI & Data Foundation；AIRSEAI 1.0 的软件栈和 Apache-2.0 许可证可在官方 GitHub 仓库核验。[1] [2]

## 1. 结论与证据等级

AIRSEAI 1.0 的本轮更新价值并非提出新的端到端 VLA 学习算法，而是提供一个可审计的**模块化具身系统集成基线**：语言理解/任务规划、语义地图、定位与导航、视觉感知、抓取和机器人接口由独立 ROS 2 模块组织，并针对“导航—抓取”可分解的移动操作任务给出明确的硬件与软件依赖。[2]

该结论的证据分级见下表。Linux Foundation 的新闻稿可以证实托管与生态治理事件，但其中关于 AIRSEAI 2.0、3.0 的内容是路线图；它们不能被写成已发布功能或实验结果。[1]

| 结论 | 证据等级 | 依据与边界 |
|---|---|---|
| AIRSEAI 已加入 LF AI & Data Foundation | B | Linux Foundation 2026-08-26 官方新闻稿。[1] |
| AIRSEAI 1.0 提供模块化移动操作软件栈与硬件/环境清单 | A | 官方代码 README、目录和 LICENSE。[2] |
| 1.0 可组合 LLM 规划、传统导航和视觉抓取模块 | A | 官方架构说明与模块清单。[2] |
| 2.0 的触觉、模型库与 3.0 的异构协同 | B | 官方路线图，**未作为已部署能力或可复现实验写入**。[1] |

## 2. 问题设定、符号与假设

AIRSEAI 面向移动操作任务：给定自然语言指令 $\ell$、传感器观测 $o_t$、地图与对象记忆 $\mathcal M_t$、机器人状态 $x_t$，系统应把指令分解为导航子目标和抓取子目标，再通过各执行器完成闭环动作。官方 README 明确将当前场景限制为可以拆解成连续导航和抓取动作的任务。[2]

记任务规划器为 $\mathcal P$，语义定位/导航栈为 $\mathcal N$，感知与抓取栈为 $\mathcal G$，执行器接口为 $\mathcal E$。基于官方模块接口的系统级形式化为：

$$
\begin{aligned}
q_{1:K} &= \mathcal P(\ell,\mathcal M_t),\\
\mathcal M_{t+1} &= \mathcal U(\mathcal M_t,o_t),\\
a^{\mathrm{nav}}_k &= \mathcal N(q_k,\mathcal M_{t+1},x_t),\\
a^{\mathrm{grasp}}_k &= \mathcal G(q_k,o_t),\\
x_{t+1} &= \mathcal E\!\left(x_t, a^{\mathrm{nav}}_k, a^{\mathrm{grasp}}_k\right).
\end{aligned}
$$

这里的公式是对公开架构的**补充系统形式化**，不是项目方宣称的训练损失。它依赖四个可检验假设：地图与里程计足以支持定位；语言规划能生成可执行子目标；视觉检测、分割和抓取姿态在目标域中有效；模块间 ROS 消息、坐标系和时钟保持一致。[2]

## 3. 方法与完整推导

系统的关键设计是把语义任务转为传统机器人栈可消费的中间变量，而不是让大模型直接输出底层电机命令。公开说明给出了两条主要链路。

第一条是导航链路。规划器将 $\ell$ 分解成对象或地点目标 $q_k$；语义地图把对象名解析成地图目标；定位模块融合 LiDAR 与 IMU 产生位姿估计；全局/局部规划与底盘控制器生成速度和 twist 命令。其数据流可写为：

$$
\ell \xrightarrow{\mathcal P} q_k \xrightarrow{\mathcal M} p_k
\xrightarrow{\text{localization+planning}} (v_k,\omega_k)
\xrightarrow{\text{base controller}} u^{\mathrm{base}}_k .
$$

第二条是抓取链路。给定目标名称，GroundingDINO 输出候选框 $b$，SAM 在 $b$ 的条件下产生像素级掩码 $m$，GraspingNet 从 RGB-D 观测提出抓取候选集合 $\mathcal H$，再以目标掩码筛选候选抓取姿态：

$$
\begin{aligned}
b &= f_{\mathrm{det}}(I, q_k),\qquad m=f_{\mathrm{seg}}(I,b),\\
\mathcal H &= f_{\mathrm{grasp}}(I,D),\qquad
h^* = \arg\max_{h\in\mathcal H}\; s(h\mid m),\\
u^{\mathrm{arm}}_k &= \mathcal C_{\mathrm{arm}}(h^*).
\end{aligned}
$$

这同样是依据公开模块说明写出的接口推导。代码仓没有给出一个统一端到端损失函数，也没有公开说明 AIRSEAI 1.0 以统一数据集训练过一个专有 VLA，因此不应把该系统描述为已验证的端到端学习策略。[2]

## 4. 训练和推理算法

AIRSEAI 1.0 的公开材料更接近部署软件的推理工作流，而非端到端训练配方。一个保守的在线执行伪代码如下：

```text
输入：语言指令 ℓ，当前观测 o_t，地图 M_t，状态 x_t
1. 以 planner 生成子任务序列 q_1:K
2. 对每个 q_k：更新定位与语义地图
3. 若 q_k 为导航：规划无碰撞路径，发布底盘控制命令并监测到达状态
4. 若 q_k 为抓取：检测 → 分割 → RGB-D 抓取候选 → 掩码筛选 → 机械臂控制
5. 接收模块状态；失败时由上层重新规划或报告失败
输出：任务状态、导航/抓取执行记录
```

公开仓库给出的环境是 Jetson Orin AGX、JetPack SDK 6.0、Ubuntu 22.04、ROS Humble、Python 3.10 与 PyTorch 2.3.0；当前硬件配置包括 AirsBot2 底盘、myCobot 630、RealSense D435、ZED2、Helios 32 LiDAR 和 CH104 IMU。[2] 这些是 1.0 的可复查依赖，而不是跨硬件平台的性能保证。

## 5. 实验设计、基线与结果

本轮未发现 AIRSEAI 1.0 的同行评审论文、统一基准表、trial 数、均值/方差、显著性检验或公开真实任务成功率。因此，不能把官方演示或新闻稿解释为可与 VLA、世界模型论文直接比较的实验结果。

| 审计维度 | 可公开核验内容 | 缺失或不可比项 |
|---|---|---|
| 任务 | 导航与抓取可分解的移动操作流程 | 标准任务数、成功定义和初始状态随机化未见统一披露 |
| 本体/传感器 | AirsBot2、myCobot 630、LiDAR、IMU、D435、ZED2 | 跨本体迁移测试未见 |
| 软件 | ROS Humble 模块、规划/感知/抓取/接口目录 | 端到端模型训练预算与版本锁定不完整 |
| 评测 | 官方代码提供部署步骤与模块接口 | 没有同数据、同硬件、同安全约束下的基线统计 |
| 产业状态 | Linux Foundation 官方确认项目托管 | 路线图不等于已交付能力 |

因此，本条目应作为**工程架构与开放资源更新**阅读，而非性能排行榜证据。

## 6. 失败模式、局限性与复现条件

该架构最突出的风险来自模块接口：语言目标到语义地图的歧义、LiDAR-IMU 位姿漂移、相机与机械臂坐标标定误差、目标检测/分割漏检，以及抓取候选与碰撞约束不一致，都可能使上层计划正确但执行失败。模块化能帮助定位错误来源，却不能自动消除误差传播。

复现还受硬件与外部依赖制约。官方仓库记录了多个第三方模型、数据和容器/依赖下载路径，但不把它们打包成可独立验证的统一权重、数据集和 benchmark artifact。[2] 任何复现报告都应记录 Jetson/传感器版本、坐标系、ROS topic 配置、外部模型版本、网络拓扑与安全停止机制；不应直接复制 README 中的高权限或网络暴露命令。
