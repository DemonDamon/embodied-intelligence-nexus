## 2. “更新”指令的固定动作

当用户未限定来源、时间范围或主题，只提出“更新”时，必须把本表两个 P1 合集纳入默认发现池，并按以下顺序执行：

1. 同步仓库并从最近一次已归档的来源台账、相关章节 README 和 Git 日志确定增量窗口。
2. 打开两个合集，优先读取最新文章；按 URL、标题和原始研究实体去重。
3. 仅处理位于增量窗口内、或因新增代码/模型/数据/正式版本而值得补档的候选。若合集不能完整加载，登记可见条目和访问限制，不以缺失页面断定“没有更新”。
4. 将每个候选映射到 VLA/VLM、世界/动作模型、操作/人形、IL/RL/Sim-to-Real、数据集/基准、工具链或产业等方向，再按照 `source-registry.md` 回溯 A/B 级来源。
5. 至少有一个 A 级来源才可进入候选评估；缺少 A/B 级来源的内容只写入永久来源台账，并保留原文 URL、标题、合集、访问日期、待回溯实体和排除/待升级理由。
6. 对通过门槛的核心主题，完成理论/实验/复现审计，按最贴近的课程章节或 `researches/` 独立归档，并更新父级和根级 README。

用户如果额外指定时间范围、技术方向、文章链接或“只看深蓝具身智能”，应以该限制覆盖默认范围，但两个合集仍可作为相关线索的回溯入口。

## 3. 公众号内容的使用边界

| 允许 | 不允许 |
|---|---|
| 从文章标题、正文、引用和合集分类中识别论文、作者、实验室、公司、代码库、模型或数据集候选 | 将文章中的技术机制、量化指标、融资、估值、发布日期、开源状态或行业判断直接写入技术文档 |
| 保存文章 URL、标题、合集名称、发现日期与主题标签，确保候选可追溯 | 因标题带有“独家”“盘点”“最新”“标杆”而默认其全面、准确或具有权威性 |
| 以文章给出的关键词检索论文、官方项目页、GitHub、模型卡、数据卡、会议页和公司官方发布 | 将公众号转述当作论文、官方声明或可复现实验 |

## 4. 每轮扫描的最低台账字段

将本来源命中的候选先记录在临时 `research_scan_notes.md`，至少包含：`合集名称`、`文章 URL`、`文章标题`、`发现日期`、`主题`、`原始实体`、`建议章节`、`C 级来源标记`、`已回溯的 A/B 级链接`、`最终处置`。临时台账不得提交；需要长期保留的线索应进入 `researches/{YYYY-MM}-wechat-.../README.md`。

## 5. 扩展规则

新增公众号时，必须记录稳定账号/合集入口、覆盖主题、优先级、来源等级和扫描说明。除非用户明确提高优先级，新增公众号默认 C 级发现源；不得为任何公众号配置“直接作为技术证据”的例外。
